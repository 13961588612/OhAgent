## 2. 我理解到的机制

### 2.1 三个"配置视图"不能混

| 视图 | 怎么拿 | 特点 |
|---|---|---|
| 文件原文 | 直接读 `$env:OPENHARNESS_CONFIG_DIR\settings.json` | 写下的原始值，可能含拼写错误与未知字段 |
| 解析后视图 | `uv run oh config show` | 合并环境变量 / profile / 默认值并脱敏，实测 257 行 |
| 运行时视图 | `uv run oh --dry-run` 的 Resolved Settings | 会话真正采用的值 |

三者不一致时，**以解析后视图为准**（s00 步骤 9 的结论在这里复用）。

### 2.2 优先级（实测）

从高到低：CLI 参数 → `OPENHARNESS_*` 环境变量 → 原生 `ANTHROPIC_*` / `OPENAI_*`（**仅当活动 profile 未显式配置该字段**）→ 活动 profile 的字段 → `settings.json` 顶层字段 → 内置默认值。

反直觉点：`OPENHARNESS_PROFILE` 只更换**活动 profile 名**，不直接改任何字段值。

### 2.3 两类作用域

| 维度 | 全局 | 项目级 |
|---|---|---|
| 路径 | `$env:OPENHARNESS_CONFIG_DIR`（默认 `~/.openharness/`） | `<cwd>/.openharness/` |
| 决定因素 | 环境变量 | 当前工作目录 |
| 存放内容 | `settings.json`、凭据、会话、cron | `issue.md`、`pr_comments.md`、`autopilot/*` |
| 是否被 git 忽略 | 是 | 是（快照 `.gitignore` 含 `.openharness/`） |

### 2.4 写配置有两条路径，能力并不一致

| 入口 | 嵌套键 | 枚举字段 | 校验实现 |
|---|---|---|---|
| `oh config set`（`cli.py:2014`） | 支持点号键 | ⚠ 直接崩溃 | `_config_coerce_value`（只认 bool/int/float/list） |
| `/config set`（`registry.py:1135`） | 不支持（只查顶层键） | ❌ 报未知键 | `_coerce_setting_value`（额外支持 `Literal` 校验） |

两者最终都调用 `save_settings()`，写的是同一个文件——所以"同一件事两套实现"必然分叉。

## 5. 企业视角

把"配置系统"放进公司平台，缺口有四个：

1. **凭据落盘**：默认把 api_key 明文写进 `settings.json`，是单用户模型的产物。企业必须改为环境变量 / KMS 注入，并把该文件纳入"含密文件"管理。
2. **配置分层缺失**：33 个字段里，"平台策略"（`base_url`、`permission.mode`、`mcp_servers`、`sandbox`）与"用户偏好"（`theme`、`vim_mode`）同处一个文件，无法做到"平台下发 + 用户有限覆盖"。
3. **写路径双实现**：`oh config set` 与 `/config set` 各带一套校验，已经出现行为分叉（枚举崩溃 vs 报错、嵌套键支持与否）。自研入口必须收敛到单一权威实现。
4. **漂移检测的前提**：技能/命令数量随 `cwd` 变化（10 vs 8），任何配置基线比对都要先固定工作目录，否则数字不可比。
